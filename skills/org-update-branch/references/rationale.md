# Why org-update-branch is built this way

- **A merge, not a rebase.** Once a branch is pushed and main has moved, the secretary cannot force-push a rebase, so main is merged in and the next push is a fast-forward.
- **The protected-path preflight.** In a worker, the sandbox protects `.claude/skills/**`, `.claude/hooks/**`, `.claude/settings.json` and `.claude/settings.local.json`; an incoming range that touches one stops a rebase (and a merge writes them the same way). The script names them and refuses, leaving the branch unchanged, instead of failing halfway. The secretary runs the same command outside the sandbox, where the check is off.
- **The acceptance gate and a merge.** The predecessor's gate required the test commit's parent to equal the merge-base, and a merge moves the merge-base to main's tip, so a merge made here does not ride the automatic merge in `acceptance` mode; a person decides that PR. While nothing is pushed, the worker rebases (no force needed, test commit stays first). A gate that served this tool would need to accept a test-commit parent that is an ancestor of base, ignore join commits before the test commit, and check declared and protected paths against the branch's own commits only.
