# Why org-start is built this way

- **Refuse inside an agent.** The first `hc` command starts a core if none runs, and that core inherits the shell's environment. A core started from an agent would carry the agent's session variables into every terminal, so the script refuses when they are set. It cannot yet tell whether a running core was started that way; the template's `env -u ...` prefix is the second line of defence.
- **Notes off.** The core's notes feature must be off in its own config. org-start checks and says what to add but never writes the core's config, which is the person's.
- **Role files live in the bin folder, not beside the templates.** The worker settings deny reading the core's folder, so a worker could not run the org script there; and the core lists every `*.md` in its templates folder as a template, so a rules file there showed up as a broken one. The bin folder is denied for writing, so a worker cannot rewrite its own rules or settings.
- **Absolute paths of `claude` and `codex` are recorded.** Templates and the review gate run in shells whose `PATH` may lack them; recording the path at start removes that dependence and gives a clear error when `claude` is missing. The gate runs codex when it is found, and otherwise Claude (`claude -p`, a fresh session with read-only tools) through the same `claude-path`: a review by the model family that wrote the change is weaker than one by a different model, but better than none, so codex stays first.
- **Folder trust for the secretary only.** A new terminal in an untrusted folder stops at Claude Code's trust dialog and the first message never arrives. org-start answers it once, for the secretary's own folder (`trust-dialog.sh`, shared with secretary-handover), with a screen read, a cursor check and no blind Enter. Worker worktrees get no keys from org-delegate: trust there follows the project, and the secretary's prompt skill handles a dialog that does appear.
- **The secretary's `--cwd` is its own folder, `<state>/secretary`** (decision 0014 F), outside every git checkout: its rules are that folder's `AGENTS.md`, imported by a one-line `CLAUDE.md`, so they hold in every turn and survive compaction, and its settings deny editing either file. Its tools are found through `PADDOCK_HOME`, the checkout path org-start records in `paddock-home`, not through the working folder. A finished secretary terminal is removed before a new one starts.
- **The mod is placed, not opened.** Opening the dialog is a separate herdr-app step that can toggle; it is not scripted until an idempotent form is measured.
- **A worker holds no GitHub credential.** It reads its base from the project clone's `origin/*`, which the secretary fetches, so org-start asks the person for no token.
- **A worker writes only its own files in the state folder,** named in its own settings file, so the shared settings never grant the state folder to the sandbox.
- **Layout and secretary prop.** An installed layout's `"secretary"` prop is kept on reinstall; when the app sees the core as another machine, the prop is written `<machine>/<secretary name>`; on WSL the Windows app is used when only its socket exists.
- **Placing again needs no login shell.** The login-shell rule exists because the first `hc` call can start a core that inherits the shell. `--place-only` calls no `hc` and starts nothing, so it is safe inside the secretary; that lets a landing reach the placed copies without a person. It places from the fetched origin branch, since a merge on GitHub leaves the local checkout as it was. It then fast-forwards that checkout too, because org-delegate and the secretary's own scripts read the checkout, not the placed copies; only a clean checkout on that branch and behind it, so it never moves a branch with someone's work on it or merges anything. Pointing org-delegate at the placed copies instead would still leave the secretary's `scripts/org` and skills stale.
