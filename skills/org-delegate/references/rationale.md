# Why org-delegate is built this way

- **Trust follows the project.** Measured once (hc 0.1.18, Claude Code 2.1.322): with the workers folder trusted, a worktree of a fresh scratch repository still raised Claude Code's trust dialog while a worktree of an already trusted clone did not. So org-delegate presses no keys; a person (or the secretary, from the screen, never blind) answers the dialog once.
- **The cache variables are written out as `/tmp/claude-<uid>/...`.** Claude Code does not expand `$TMPDIR` in a settings `env` value (measured: the variable printed back unexpanded), so the sandbox's temporary folder is spelled out. A host check showed `npm pack` finished without a read-only file system error.
- **The socket folder is per user,** so the shared settings file cannot name it; it comes from the environment (`PADDOCK_CORE_SOCKET_DIR` or the folder of the terminal's socket) and the script stops before creating anything when it has neither.
- **A `.gitignore` for what paddock places.** `settings.local.json` and the `.gitignore` itself are ignored so that staging everything in the worktree never commits them; a base that tracks its own `.claude/.gitignore` keeps it.
- **The worker's own settings file, not `allowWrite` in the worktree.** The worker settings turn off unsandboxed reruns, which makes the sandbox admin-required, and Claude Code then ignores an `allowWrite` in the worktree's settings files. So the writable paths live in `<state>/settings/<id>.json`, generated from the shared template, and only the worker's own event, sequence and lock files are in it (they must exist first, because the sandbox binds files). A file-tool hook refuses the rest of the state folder rather than an `Edit` deny, since Claude Code turns that deny into a sandbox `denyWrite` that beats the own-file entries. A worker therefore cannot rewrite its settings or write as another id.
- **The review gate's calls are exact strings in `excludedCommands` and `allow`.** The reviewing CLI starts its own sandbox and cannot start inside the worker's, so the two argument-free calls run outside it. The base it reviews against is read from `<state>/bases/<id>`, a file the secretary writes and the worker cannot, so a worker cannot move the base it is reviewed against.
- **No git config is written.** Using `worktree add --no-track` and a base file keeps the shared `.git/config` untouched, so a leftover `config.lock` placeholder from a killed worker never blocks or delays a delegate.
- **The start record is written before the launch,** so the worker's own later `done` or `blocked` is the latest record and is not hidden by it.
- **The task travels in the launch,** so nothing is typed into the worker afterwards; no `AGENTS.md` or `CLAUDE.md` is written into the worktree because it would collide with the target repository's own files. Role rules come from the worker template.
- **No GitHub credential for the worker.** It gets an empty `GH_CONFIG_DIR` and no token variables and reads its base from the project clone's `origin/*`, which the secretary fetches; a stale base is reported to the secretary, which fetches and answers.
- **The secret block is off by default** because it costs the project: the worker's own programs and tests cannot open the denied files either, and measurement showed an `allowRead` entry does not win over `denyRead`, so example files are readable with the Read tool only. Hence secrets must come from the environment or from files the patterns do not name.

### The steps in full

1. **Checks before it creates anything.** The arguments, `hc ls` (the core answers), and that no terminal named `w-<id>` exists (exit 7). A `task_id` is lowercase letters, digits, `_` and `-`, not starting with `-`, at most 30 characters.
2. **Worktree.** If the project has an `origin`, it runs `git fetch origin` first and, when `origin/<base>` exists, branches from that (a failed fetch exits 6 before anything is created; `--no-fetch` skips both and uses the local base). Then `git -C <project> worktree add -b <branch> $PADDOCK_WORKERS_DIR/<id> <base>`. The workers folder (default `~/paddock-workers`; `PADDOCK_WORKERS_DIR` must be an absolute path, else exit 2) is the one folder trusted once per machine; measured once (hc 0.1.18, Claude Code 2.1.322), with that folder trusted a worktree of a fresh scratch repository still raised the dialog while a worktree of an already trusted clone did not, so trust appears to follow the project the worktree belongs to, not the folder it sits in; the script checks the worktree landed directly inside it, and refuses a path that already exists (exit 6).
3. **Settings.** Writes `<worktree>/.claude/settings.local.json` with `hc file write`: `{"sandbox":{"filesystem":{"denyRead":[<socket folder>],"denyWrite":[<socket folder>]}}}` and `env` with `npm_config_cache`, `UV_CACHE_DIR` and `PIP_CACHE_DIR` set to `/tmp/claude-<uid>/{npm,uv,pip}-cache` (the sandbox's temporary folder, written out because Claude Code does not expand `$TMPDIR` in a settings env value: measured with `claude -p` 2.1.322, `PADDOCK_ENVX=\$TMPDIR/envx-cache` printed back unexpanded). Host check (Claude Code 2.1.322, this settings file plus the shipped worker settings, `claude -p` with two Bash calls): the variables read `/tmp/claude-1000/{npm,uv,pip}-cache` with `TMPDIR` = `/tmp/claude-1000`, and `npm pack ./pkg --dry-run` exited 0 with no read-only file system error (the sandbox blocked the registry call, the pack still finished). The socket folder is the core's (`$XDG_RUNTIME_DIR/herdr-core` on Linux): per user, so the shared settings file cannot name it; it is `PADDOCK_CORE_SOCKET_DIR`, else the folder of `$HC_TERMINAL_SOCKET`, and with neither the script stops before creating anything (exit 2). This also applies to every probe that calls org-delegate: run one from outside a core terminal with `PADDOCK_CORE_SOCKET_DIR="$XDG_RUNTIME_DIR/herdr-core"` (Linux). Only what changes per task or per user goes here; the role's deny list, sandbox and hooks come from the worker template's `--settings` file. It refuses (exit 6, worktree removed) when the base tracks a `.claude` symlink or a `settings.local.json`: nothing is written through a symlink and no file is overwritten. It also writes `<worktree>/.claude/.gitignore` naming `settings.local.json` and itself, so what paddock places is ignored by version control and staging everything does not commit it; a base that tracks its own `.claude/.gitignore` keeps it. Other untracked files a worker may see (`.bashrc`, `.mcp.json`, `.gitconfig` and so on) are not placed by this script.

   **The worker's own settings file.** The worker settings set `sandbox.allowUnsandboxedCommands` false, so no command is rerun outside the sandbox; by the vendor docs that makes the sandbox admin-required, and Claude Code then ignores an `allowWrite` in the worktree's `.claude/settings*.json` (the deny entries there still apply). So `allowWrite` goes elsewhere: `scripts/org --as secretary own_files w-<id>` creates the worker's own files in the state folder (this month's and next month's `events/<YYYY-MM>/w-<id>.jsonl`, `events/w-<id>.seq`, the lock folder `locks/w-<id>`; the sandbox binds files, so they must exist first), and the script writes `<state folder>/settings/<id>.json`: `templates/worker-settings.json` with its empty `"allowWrite": []` filled with those paths and the `--allow-write` paths. The worker template passes that file with `--settings` when it exists for the worktree's folder name, else the shared one. The worker can write nothing else in the state folder (the shared settings allow none of it to the sandbox, and a `PreToolUse` hook refuses the file tools there; not an `Edit` deny, which Claude Code turns into a sandbox `denyWrite` that beats the own-file entries), so it cannot rewrite its settings file or write as another id; readers take the sender from the file name (`scripts/org`). Exit 12 if the files cannot be made. The same file carries the review gate's two argument-free calls (`bash "<bin>/second-model-review.sh"` and with `--design`, path quoted and not) as exact strings in `sandbox.excludedCommands` and `permissions.allow`: the reviewing CLI starts its own sandbox and cannot start inside the worker's, and the base it reviews against is the one the script recorded in `<state folder>/bases/<id>` (a file the secretary writes and the worker cannot, read by the gate outside the sandbox; a worktree from before that has it as `branch.<name>.paddockBase` in git config, which the gate reads when the file is absent). The script writes no git config at all (`worktree add --no-track`, no `paddockBase`), so a worker's `.git/config.lock` placeholder no longer blocks or delays a delegate.
4. **Record.** `bash "$root/scripts/org" --as secretary report start --task <id> --to secretary "Delegating to w-<id> ..."`, written before the launch so that the worker's own later `done` or `blocked` is the latest record in `list_runs` and is not hidden by this one. If it cannot be written, nothing is started (exit 12). A failure after this point that leaves no worker appends a `blocked` record.
5. **Launch.** `hc run --bg --outlive-parent --name w-<id> --cwd <worktree> --label task_id=<id> worker "<text>"`. The text is `Your org id is w-<id>. Your task id is <id>.` and a blank line, then the task. The task travels in the launch, so nothing is typed into the worker afterwards. If `hc run` fails, the request may still have been accepted: the worktree and branch are removed only when `hc get w-<id>` answers `not_found`; otherwise everything is kept and the terminal, worktree and branch are named (exit 5).
6. **First message.** `first_message.sent` must be `true`; a missing or unreadable answer counts as not sent. If not (exit 10), the script prints the result and leaves the worktree and terminal as they are. It presses no keys and kills nothing. Read the worker with `hc read w-<id>`. It saves the first message and, with `--title`, the work entry in `<state>/resend/<id>/` (`message`, `entry`); at the folder-trust dialog, `org-escalation answer --text yes` sends and writes them (`scripts/resend.sh <id>` does the same by hand: exit 12 not sent, 13 sent but the entry not written; both keep what is left). A new delegate with the same id drops the leftovers.

7. **Work entry (`--title` only).** After the first message was sent, adds `{"task_id","title","since","worktree","task"}` to `org-state.work` with `bash "$root/scripts/org" --as secretary doc update org-state` (a null or absent document becomes `{"work":[<entry>],"approvals":[]}`; other entries are kept). `since` is the UTC time of the write, `worktree` the worktree path, `task` the task text as given; strings are JSON-escaped, and the entry is placed by a scan that skips string contents, so braces and brackets in the task do not matter (org-suspend and org-resume read it back). A failure to write it leaves the worker running and exits 13. After a failed launch (any exit above) no entry is written.

### Trust of a repository made for a task (measured)

**Trust: measured, the parent folder is not enough.** Host probe `scripts/probes/folder-trust-local-parent.sh` (2026-11-14, decision 0010 point 3): a parent folder trusted by answering the dialog once; a repository made inside it afterwards still raised the dialog, in the repository itself (`repo-in-parent`) and in its worktree outside the parent (`wt-outside`); the untrusted control raised it too. So each new repository raises the dialog once: after `org-delegate` exits 10, read the screen with `hc read w-<id>` and answer it from there (never a blind Enter: the default is "No, exit"). No script writes Claude Code's configuration.

### Secret block (measured)

A worker reads everything in its worktree unless the project turns the block on: the `secret-block` column of its row in `projects.md` (or `--secret-block`, which wins) is `on` (`.env`, `.env.*`, `credentials*`, `*.pem`), `off`, or comma-separated patterns that replace those. On, the per-task settings file also gets `Read(**/<pattern>)` deny rules plus `Read(!**/*.example)` (the Read tool), absolute `sandbox.filesystem.denyRead` entries `<worktree>/<pattern>` and `<worktree>/**/<pattern>` (programs). There is no `allowRead` for example files: it was measured that it cannot reopen them (below), so it is not written. **What the project loses:** the worker's own programs and tests cannot open the denied files, or the example files, either (the Read tool can read the examples; an app that loads `.env`, a `credentials` module, a test certificate); secrets have to come from the environment or from files the patterns do not name. Measured (host probe `scripts/probes/secret-block.sh`, decoys only, Claude Code 2.1.322): `Read(!**/*.example)` works, the Read tool reads example files; the sandbox `allowRead` entry does NOT win over `denyRead`, so a `cat` or `awk` of an example file (also a nested one) is refused. Example files are readable with the Read tool only, not by programs. An `allowRead` entry is not written because it was measured not to reopen them.
