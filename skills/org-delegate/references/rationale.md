# Why org-delegate is built this way

- **Trust follows the project.** Measured once (hc 0.1.18, Claude Code 2.1.322): with the workers folder trusted, a worktree of a fresh scratch repository still raised Claude Code's trust dialog while a worktree of an already trusted clone did not. So org-delegate presses no keys; a person (or the secretary, from the screen, never blind) answers the dialog once.
- **The cache variables are written out as `/tmp/claude-<uid>/...`.** Claude Code does not expand `$TMPDIR` in a settings `env` value (measured: the variable printed back unexpanded), so the sandbox's temporary folder is spelled out. A host check showed `npm pack` finished without a read-only file system error.
- **The socket folder is per user,** so the shared settings file cannot name it; it comes from the environment (`PADDOCK_CORE_SOCKET_DIR` or the folder of the terminal's socket) and the script stops before creating anything when it has neither.
- **A `.gitignore` for what paddock places.** `settings.local.json` and the `.gitignore` itself are ignored so that staging everything in the worktree never commits them; a base that tracks its own `.claude/.gitignore` keeps it.
- **The worker's own settings file, not `allowWrite` in the worktree.** The worker settings turn off unsandboxed reruns, which makes the sandbox admin-required, and Claude Code then ignores an `allowWrite` in the worktree's settings files. So the writable paths live in `<state>/settings/<id>.json`, generated from the shared template, and only the worker's own event, sequence and lock files are in it (they must exist first, because the sandbox binds files). A file-tool hook refuses the rest of the state folder rather than an `Edit` deny, since Claude Code turns that deny into a sandbox `denyWrite` that beats the own-file entries. A worker therefore cannot rewrite its settings or write as another id.
- **The review gate's calls are exact strings in `excludedCommands` and `allow`.** The reviewing CLI starts its own sandbox and cannot start inside the worker's, so the two argument-free calls run outside it. The base it reviews against is read from `<state>/bases/<id>`, a file the secretary writes and the worker cannot, so a worker cannot move the base it is reviewed against.
- **No git config is written.** Using `worktree add --no-track` and a base file keeps the shared `.git/config` untouched, so a leftover `config.lock` placeholder from a killed worker never blocks or delays a delegate.
- **The start record is written before the launch,** so the worker's own later `done` or `blocked` is the latest record and is not hidden by it.
- **The task travels in the launch,** so nothing is typed into the worker afterwards; no `AGENTS.md` or `CLAUDE.md` is written into the worktree because it would collide with the target repository's own files. Role rules come from the worker template.
- **No GitHub credential for the worker.** It gets an empty `GH_CONFIG_DIR` and no token variables and reads its base from the project clone's `origin/*`, which the secretary fetches; a stale base is reported to the secretary, which fetches and answers.
- **The secret block is off by default** because it costs the project: the worker's own programs and tests cannot open the denied files either, and measurement showed an `allowRead` entry does not win over `denyRead`, so example files are readable with the Read tool only. Hence secrets must come from the environment or from files the patterns do not name.
