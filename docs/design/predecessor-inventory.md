# Predecessor inventory

Status: draft. This document lists what the predecessor, claude-org-ja, distributes to its agents, enforces on them and records about them, and sorts each item for paddock. It does not decide anything that is still open: those items become questions in [open questions](open-questions.md) (Q10 to Q19).

## 1. How to read this

### 1.1 Verdicts

| Verdict | Meaning |
| --- | --- |
| **Keep** | paddock carries the line or the duty itself, usually rewritten (a template body, a skill, a Claude Code setting, a mod, a record). |
| **herdr** | herdr-core or herdr-app already does it. Used only where a herdr primary source or a measurement shows it. |
| **Retire** | Not carried. The reason is given: usually the predecessor part it served is gone (the dispatcher, renga, the broker, `state.db`'s SQLite, the separate dashboard). |
| **Open** | The way to do it is a choice nobody has made. Each Open row points to a question in [open questions](open-questions.md). |

"Open" never means "we do not know whether it can be done". That is a feasibility of **Unverified**.

### 1.2 Feasibility

Every row also says whether the verdict can be carried out on paddock's base:

| Feasibility | Meaning |
| --- | --- |
| **Feasible** | A primary source or a measurement shows it works. |
| **Not feasible** | A primary source or a measurement shows it does not work as stated. |
| **Unverified** | Not shown either way. The row gives the probe (what to run, what output would settle it). |

For Retire rows, "Feasible" means nothing paddock needs is lost by dropping it, and the basis says why.

- **Hooks**: every file in `.hooks/` and `.hooks/lib/`, and their wiring in each role's settings and in the schema.
- **Gates**: 19 tools under `tools/` (acceptance, merge, Codex, self-edit, spawn, retro, capability, notify, premise, rebase, version and drift checks, curate threshold, link audit) and the merge sections of the `org-pull-request` and `org-delegate` skills.

- **Monitoring, notification, suspend and handover**: `.dispatcher/CLAUDE.md` and every `.dispatcher/references/*.md`, the watcher, relay, cockpit and dashboard tools, `dashboard/`, `docs/operations/`, `.claude/rules/pr-ci-watch.md`, and the suspend, resume and handover skills.

Not read: backups (`*.bak*`), tests other than to learn what a tool does, per-run logs (their classes are listed), the bodies of the worktree-creation helpers in `tools/gen_delegate_payload.py` (git plumbing), the bodies of the transport prose fragments in `tools/skill_src/fragments/`, and parts of `role-pattern-sandbox-contract.md` beyond its role and pattern sections. An adversarial review then looked for what the list missed ([section 16](#16-review-notes)).

The enumeration found 338 mechanisms. Rows below group related mechanisms; [appendix A](#appendix-a-enumerated-mechanisms-per-row) lists which mechanisms each row covers. This is the range that was listed, not a claim that nothing was missed.

## 2. Probes run for this inventory

The worker that wrote this document runs in a sandbox where `hc` cannot reach or start a core (`hc ls` → `{"error":{"kind":"unavailable","message":"cannot start core: Read-only file system (os error 30)"}}`; with a scratch `HC_SESSION` and scratch XDG folders, `core did not start within 5 s` and `Operation not permitted` in `core.log`). The probes were therefore two shell scripts that the secretary ran on the host, on 2026-11-08 between 22:45 and 22:53 UTC. Each used its own core (`HC_SESSION=pinv` and `pinv2`) and its own template folder (`XDG_CONFIG_HOME` under `/tmp`), never the default core, and stopped only its own core at the end. hc 0.1.18, Claude Code 2.1.319 (`--model sonnet --permission-mode default`), WSL2. Each worktree was a fresh `git init` folder with no CLAUDE.md.

| Probe | Question | Result |
| --- | --- | --- |
| P1 | Can delegation write `AGENTS.md` and `.claude/settings.local.json` into a fresh worktree with `hc file write`, when `.claude/` does not exist yet? | **Yes.** All three files (`AGENTS.md`, `.claude/settings.local.json`, a hook script) were written; the missing folder was created, as [rpc] `file.write` says ("making missing folders"). A new file gets mode 644, so hooks are called as `bash <path>`. |
| P2 | Does a Claude Code launched from an `hc` template (`hc run --cwd <worktree> <template> "<task>"`) load that `settings.local.json` and read that `AGENTS.md`? | **Yes, once the folder is trusted** (see P6). It answered the codeword written only in `AGENTS.md`; `touch denied-probe.txt` was refused by `permissions.deny` ("2 actions not run · permission denied"); `touch hooked-probe.txt` was refused by the `PreToolUse` hook (exit 2, its stderr `PROBE_HOOK_DENY` quoted back by the agent); the `SessionStart` hook ran. Neither file was created. |
| P3 | Can OSC 7501 `done` stand in for the `Stop` hook as "the turn has ended"? | **For observing, yes; for holding a turn open, no.** A `Stop` hook that blocked once (exit 2) ran at 22:46:47.744; the agent continued, and the second `Stop` (allowed) ran at 22:46:49.295. Core recorded exactly one `done` status (`status_ms` 22:46:49.320, 25 ms after the allowed `Stop`) and one `turn` event (`turn: 1`) for the whole task. No `done` was reported for the blocked stop. `done` marks the end of a turn after the `Stop` hooks have let it end; it cannot make an agent keep working. |
| P4 | Does a `settings.local.json` with only `deny` and hooks (no `allow`) avoid the folder-trust dialog? | **No.** The dialog appeared and `first_message.sent` was `false`. After it was accepted, deny and hooks worked as in P2. |
| P5 | Does passing the role's settings on the template's command line (`command: claude ... --settings <file outside the worktree>`) avoid the dialog, and do they apply? | **They apply; the dialog still appears.** After the dialog, the `deny` rule and the `PreToolUse` hook in the `--settings` file both refused their commands, and the `SessionStart` hook ran. |
| P6 | Control: a worktree with only `AGENTS.md`. | **The dialog appears for every new folder**, settings or not. Each launch returned after about 58 s with `first_message: {sent: false, reason: "it never reported its status, so it may be showing a dialog ..."}`; the screen showed "Quick safety check: Is this a project you created or one you trust?". In batch 1 the dialog also listed "This folder pre-approves 1 tool permission in .claude/settings.local.json: Bash(ls:*)". The scripts accepted it with `hc keys <t> down enter`, as [skill] describes, and then sent the task with `hc send`. |
| P7 | What environment does a program in an hc terminal get? | **The environment of whatever started the core.** The core was started by the script, which ran under the secretary's Claude Code session. A plain `sh -c 'env'` in an hc terminal saw the same 15 `CLAUDE*` variables as the script, including `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`. Every probe Claude showed "Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker", and no session log was written. |
| P8 | Which Claude Code hook events fire in a template launch (Issue #49)? | **All seven probed.** Settings passed with `--settings` in the template's `command`, marker-writing hooks, hc 0.1.18, 2026-11-10 (`scripts/probes/hk18-hook-events/`). Order of markers: `SessionStart`; `UserPromptSubmit` (the template's first message); `Stop`; `UserPromptSubmit` (a task sent with `hc send`: one Bash command); `PreToolUse` (`Bash`); `PostToolUse` (`Bash`); `Stop`; `PreCompact` (after `/compact` typed with `hc send`); `SessionStart` again (re-fired after the compact); `Notification` (about 60 s later, no permission prompt pending, empty prompt on screen). Counts: `SessionStart` 2, `UserPromptSubmit` 2, `PreToolUse` 1, `PostToolUse` 1, `PreCompact` 1, `Notification` 1, `Stop` 2. The folder-trust dialog did not appear in this run. Not measured: the event-specific payload fields (`trigger`, `tool_name`, `message`, the `Notification` type), because the hook cut its input at 300 characters; whether `Notification` also fires for a permission prompt. |

What the probes did not cover: a Claude Code started by a person in the window, remote machines (`--on`), Windows, and whether a parent folder's trust covers a new worktree below it.

### 4.1 PRM-11: does the `org` mailbox carry a per-client permission tier

**Decided by the owner, 2026-11-11: no tier in the `org` script for now. Paddock relies on L-N2 and L-N8, and a narrower write surface is measured first as a separate step (below).** Issue #30; the follow-up is Issue #160.

**Why.** A tier inside `scripts/org` would be a check by convention: the mailbox store is plain files that a worker is allowed to write directly, so a caller that skips the script is not bound by it. A tier that binds needs either a resident server that is the only writer of the store, or a write surface narrowed per worker. The first reverses the choice of Q8 (b) (no resident process, `scripts/org` line 4); the second does not exist yet. The predecessor's tier had a server in the path of every call; paddock's mailbox has none by decision (0002, 0004, Q8 (b)), so the structural lines can only sit in the sandbox and in the core's access (L-N2, L-K4).

**What the mailbox is today** (all in `scripts/org`):

- Who may call what: every command is open to every id. The only gate on the commands is that the id is well formed (lines 54 and 59). The one gated command is `doc set` and `doc update`: they refuse any id but `secretary` or `$PADDOCK_SECRETARY_NAME` (line 257, exit 7). `doc get` is open.
- How `--as` works: the id is `--as <id>` or `$PADDOCK_ORG_ID` (lines 48 to 50). It is the caller's claim. Nothing is checked against it: no token, no peer check. A worker's id is given in its task text (`templates/worker.md` line 15: "Your id is `w-` plus the task id, and the task text gives it"; `templates/worker-rules.md` line 12).
- What stops a worker from writing as the secretary: no check in the script. The write surface is `~/.local/state/paddock` as a whole (`templates/worker-settings.json` lines 26 to 28), not the worker's own file. Measured 2026-11-10 (row L-K4): a worker appended to its own history file through the org script and directly from Bash, and a write outside the folder was refused by the sandbox. Nothing was measured for another id's file.
- What stops a worker from writing `org-state`: the id check at line 257, which is the same claim; then the call goes to the core through `hc connect` (line 268 and following). The `Bash(hc:*)` deny (`templates/worker-settings.json` line 5) does not match `bash scripts/org ... doc set`, because it matches command text. What would stop it is L-N2's holders. As measured 2026-11-11 (row L-N2): the deny rule refuses a direct `hc` call; the worker environment carries no `HC_` variable; the core's socket folder is named in the per-task settings, but its effect is not measured, so whether a caller that does not match the deny rule reaches the core is not known.

**Could a worker call `scripts/org --as secretary` today, and what follows** (from reading the script; not tried against a real mailbox): yes, nothing in the script refuses it. Then:

1. `send_message` writes a line with `from: secretary` into the secretary's own history file (lines 127 and 128, `$d/$id.jsonl`). The recipient sees it as the secretary's.
2. `report` does the same with a run record, and `list_runs` (line 232 onward) shows the latest record per task with the secretary as writer.
3. `check_messages` without `--peek` writes acks into the secretary's file (lines 190 to 193). The acks mark the secretary's unread mail as read (lines 145 to 147), so the real secretary never sees it.
4. `doc set org-state` passes the script's check; it is stopped, if at all, by L-N2 (above).
5. The same effect needs no script: the worker may append a hand-written line to the secretary's file with Bash (measured for its own file as L-K4; the sandbox rule is per folder, `templates/worker-settings.json` line 27).
6. It reaches the privileged paths, not only the mailbox. The approval card sends the person's answer as an ordinary mail from id `person` (`mods/org-cockpit/main.js` line 64), and the secretary acts on `ANSWER` mails through the escalation skill (`templates/secretary.md` line 73, `skills/org-escalation/scripts/org-escalation.sh` line 170). The secretary kills and removes a worker's terminal once that worker's report is in (`templates/secretary.md` line 71). So a forged `person` answer or a false `done` report is the real exposure: an approval or a cleanup the owner did not give. This is the exposure the owner accepted for now.

Readers also trust the `from` field inside each line, not the file it came from: `window` (line 135 onward) drops the file name, `unread_lines` (line 144 onward) and `list_runs` read `from` from the text. So even a worker confined to its own file could write a line saying `from: person`.

Mail confidentiality is not held either: reads are open (`bash scripts/org --as <other> check_messages --peek` reads that id's mail without consuming it). The inventory does not say it is a goal.

**Options considered**

- **A. Carry a tier in `org`** (a worker token the script checks). Rejected for now: it needs a secret the worker cannot read, issued at delegation (Q10), and it needs the store closed to direct worker writes. Today the sandbox allows the whole folder, so a direct append skips the check. Without a resident server as the only writer (Q8 (b) reversed) or the narrowed write surface below, it adds code and no protection.
- **B. Rely on L-N2 and L-N8 alone. Chosen.** Nothing to build. Accepted exposure: a worker that ignores its rules can forge mail and records as another id, including a `person` answer and a false `done` report (point 6). It rests on L-N2 for `doc`; L-N2 is still Unverified for a caller that does not match the deny rule, so B does not yet hold there. L-N8 is reworded (below).
- **B2. Narrow the write surface (next step, Issue #160; not a tier).** Narrow the worker's `allowWrite` from the whole state folder to its own file, and make the readers take the sender from the file name (drop or flag a line whose `from` differs from its file; accept an `ack` only from its own file), with run records tied to the worker's own task id. This is what L-K4 says in words ("record files assigned to it"). It needs the per-task settings of Q10 naming the file (month folder, and `events/<id>.lock` and `.break` beside it, `scripts/org` lines 107 and 117), and a measurement that the sandbox's `allowWrite` takes a file or glob and refuses the sibling files. Not measured; nothing in this repository says it does. Reads stay open. B2 does not repair a failed L-N2: `doc` goes through `hc connect`, not the files.

**When to revisit**

- Toward A: a resident `org` server is built for another reason (Q8 (b) reversed); or workers run where the state folder is not shared by file (a second machine, 0004), so the script is the only place a check can sit; or a case where a worker did write as another id.
- Toward making B2 required: the L-N2 measurement shows a worker reaching the core, or a task where a worker's own history file is not the only path it needs.
- Away from B2: the sandbox cannot name a file or glob; then B rests on the rules and L-N2 only, and the owner accepts that.

**Measured 2026-11-11 (Issue #160 step 1, [scripts/probes/own-file-write.sh](../../scripts/probes/own-file-write.sh), decoy files, details in row L-N8):** a per-file `allowWrite` entry held for Bash (the sandbox refused the sibling and a new file in the same folder), and did not bound the Edit tool (it wrote the sibling). So B2 needs a second holder for the file tools as well as the sandbox entry.

**Step 2 (Issue #160), measured 2026-11-11 on the host (Claude Code 2.1.322, login shell, claude link unchanged, one run, decoy files only):** [scripts/probes/own-file-allow-write.sh](../../scripts/probes/own-file-allow-write.sh) runs `claude -p` with `templates/worker-settings.json` and a per-task `settings.local.json`, in a temp folder under the home folder, three runs of three Bash calls each (append to the worker's own file, append to a sibling, create a new file). **Control** (the folder in `allowWrite`): all three written, so the setup lets a write through. **`file-entry` HOLDS** (the file alone in `allowWrite`, nothing on its folder): own file written, sibling byte-identical, new file not created; both refusals were the sandbox's "read-only file system" error. **`deny-parent` DENY WINS** (the file in `allowWrite`, its folder in `denyWrite`): nothing written, the own file refused too, all three with the same error.
